## Why Airbnb belongs in this pass

Airbnb is useful to Teswa because it repeatedly handles the same kind of product tension Teswa has:

- a real-world object/context that must be judged through a screen,
- progressive trust under uncertainty,
- discovery that later becomes consequential,
- digital agreement that must survive physical reality,
- multiple product worlds that still feel like one app,
- dense information that is revealed as commitment rises.

Teswa must not inherit Airbnb's travel aesthetics, card treatment, iconography, brand palette, or hospitality metaphors.

The only useful question is:

> Which product mechanics transfer to Teswa's authored state system?

Teswa authority remains:

```text
MINE → POSSIBLE → BETWEEN US → REAL → EVIDENCE
```

# 1. All-new Airbnb app — one product, multiple worlds

Airbnb's 2025 app rebuild introduced Homes, Experiences, and Services inside one app while preserving distinct contexts. The app also changes role after a booking: discovery gives way to itinerary, check-in details, messages, and recommendations relevant to the booked trip.

Official source:
- https://news.airbnb.com/product-releases/airbnb-2025-summer-release

## TAKE

### A. Architecture can change emphasis after commitment

Before booking, Airbnb is discovery-heavy.
After booking, the product becomes trip/coordination-heavy.

Teswa parallel:

```text
before proposal → POSSIBLE
accepted proposal → BETWEEN US
physical handoff → REAL
completed outcome → EVIDENCE
```

The UI should not keep treating the user as if they are still casually browsing once a consequential shared state exists.

### B. Multiple worlds can share one shell without flattening their meaning

Homes / Experiences / Services coexist, but do not become generic identical cards in every context.

Teswa can similarly unify navigation while keeping:
- private possessions,
- public possibilities,
- offers,
- deals,
- evidence
semantically distinct.

### C. Context should travel with the user

Airbnb's Trips view keeps the booked home, itinerary and related activities connected.

Teswa equivalent:
- requested item,
- offered item,
- people,
- proposal state,
- deal state,
- meetup/confirmation context
should remain recoverable through the journey.

## DO NOT TAKE

- travel tab metaphors,
- bottom-nav labels,
- home cards,
- hospitality imagery,
- visual chrome.

# 2. Progressive trust — Guest Favorites and review dimensions

Airbnb's Guest Favorites use multiple kinds of evidence including ratings, reviews, reliability and communication; reviews also break experience into dimensions such as accuracy, communication, location and value.

Official sources:
- https://www.airbnb.com/resources/hosting-homes/a/understanding-guest-favorites-642
- https://www.airbnb.com/resources/hosting-homes/a/why-reviews-matter-41

## TAKE

### A. Trust is assembled from context-relevant evidence

This strongly supports Teswa's locked principle:

> CERTAINTY IS EARNED IN LAYERS.

Teswa should resist one giant trust score.
Different stages need different evidence:

```text
object truth → media / condition / description
person confidence → completed swaps / response behavior / reviews
real-world confidence → location / coordination / no-show history where policy allows
outcome → bilateral completion + post-deal review
```

### B. Outcome-backed evidence is stronger than profile decoration

Airbnb's trust surfaces are tied to actual trip history and reviews.

Teswa should similarly privilege evidence generated by completed exchange history over ornamental badges.

## DO NOT TAKE

- copying Guest Favorite badges,
- one-to-one review dimensions,
- public ranking systems before Teswa has enough evidence/data,
- fake certainty from tiny sample sizes.

# 3. Review highlights and comparison — progressive disclosure

Airbnb's 2026 product updates introduced review highlights that summarize large volumes of reviews around the topics relevant to a guest, plus comparison support for saved homes.

Official source:
- https://www.airbnb.com/resources/hosting-homes/a/now-theres-even-more-to-airbnb-763

## TAKE

### A. Show the evidence relevant to the decision in front of the user

Teswa should not show every fact everywhere.

Offer creation might need:
- requested object truth,
- owner openness,
- my eligible item,
- enough person evidence to make a proposal.

Deal coordination might need:
- exact item pair,
- latest agreement,
- location/meetup context,
- confirmation state.

This is much stronger than generic profile/info sections.

### B. Comparison should be relational, not isolated

Airbnb's comparison flow is useful because users often decide between possibilities rather than inspect one listing in isolation.

Teswa's Offer is even more relational:

```text
THEIR ITEM
↔
MY ITEM
```

The design should therefore optimize for comparison between the two sides rather than simply stacking two independent cards.

## DO NOT TAKE

- AI summaries by default,
- feature-heavy comparison matrices,
- travel-specific comparison dimensions.

# 4. Trips / itinerary — accepted state changes the product

Airbnb's app becomes itinerary-oriented after a booking and surfaces check-in details, schedule, messages and nearby recommendations in the context of the trip.

Official source:
- https://news.airbnb.com/en-uk/2025-summer-release-now-you-can-airbnb-more-than-an-airbnb

## TAKE

### A. Acceptance should create a different object/world

This maps almost directly to Teswa's current backend truth:

```text
Offer accepted
→ Deal identity exists
→ coordination becomes the main job
```

Do not leave the user in an Offers list with a green label.
The product should recognize that a new shared world now exists.

### B. Shared state deserves its own continuity

The pair of items + participants + current status should travel together as one consequential context.

## DO NOT TAKE

- itinerary timeline as an automatic visual metaphor,
- calendar-like UI unless Teswa later proves scheduling is central.

---

# 5. Messaging — preserve why the conversation exists

Airbnb's 2025 redesign explicitly revamped messaging to support richer trip/service context, including media and payments for service customization.

Official source:
- https://news.airbnb.com/product-releases/airbnb-2025-summer-release

## TAKE

Conversation should preserve the object/context that caused it.

This reinforces Teswa's law:

> PRESERVE WHY PEOPLE ARE TALKING.

For Teswa:
- direct conversation ≠ story/context reply ≠ deal coordination.

A unified inbox is possible.
A flattened generic chat model is not.

## DO NOT TAKE

- payments/service commerce mechanics,
- travel-message hierarchy,
- copying Airbnb message chrome.

---

# 6. Discovery + maps — possibility is affected by real-world feasibility

Airbnb's current product continues to invest in search/maps and travel-time context because physical location changes whether a digital possibility is practical.

Official sources:
- https://news.airbnb.com/product-releases/airbnb-2025-winter-release
- https://www.airbnb.com/resources/hosting-homes/a/now-theres-even-more-to-airbnb-763

## TAKE

Location should not be a decorative metadata chip if it materially changes willingness to act.

Teswa question:

> At what point does distance become decision-critical?

Candidate translation:
- discovery: approximate distance/area may be enough,
- proposal: feasibility becomes more explicit,
- deal: coordination location becomes concrete.

This again supports progressive disclosure.

## DO NOT TAKE

- map-first discovery by assumption,
- Airbnb-style destination browsing,
- location precision before the commitment level requires it.

# 7. Airbnb's strongest lesson for P2 Offer

For the current P2 lane, Airbnb does **not** provide the core proposal mechanic. Steam/eBay/Vinted are stronger there.

Airbnb's value is the **depth model around the proposal**:

```text
DISCOVERY
→ enough evidence to imagine action
→ commitment threshold
→ product changes emphasis
→ shared context persists
→ real-world event happens
→ outcome becomes future evidence
```

That is almost the same state logic Teswa authored independently.

So Airbnb should influence:
- progressive disclosure,
- context continuity,
- trust layering,
- post-commitment architecture,
- real-world transition clarity.

It should **not** influence:
- the visual shape of the Offer pair,
- the app's brand language,
- cards,
- typography,
- colors.

# P2 consequence

The next visual/interaction exploration should test three genuinely different authored models:

## DIRECTION A — PAIR BECOMES ONE OBJECT

Two possessions merge into one persistent proposal object.

Primary reference lessons:
- Steam trade relationship,
- eBay proposal state,
- Airbnb context continuity.

## DIRECTION B — CROSSING THE PRIVATE/PUBLIC THRESHOLD

The user's item visibly moves from MINE into a shared proposal field.

Primary reference lessons:
- Teswa thesis first,
- Material 3 Expressive state/motion hierarchy,
- Airbnb state-dependent architecture.

## DIRECTION C — TENSION / BALANCE

Both possessions remain distinct and the relationship between them becomes the interface.

Primary reference lessons:
- comparative decision systems,
- Airbnb progressive evidence,
- physical barter/source-world research.

No direction is approved until all three are rendered under the same content and compared side by side.

# Reference verdict

**Airbnb = strong architecture/trust/context reference, weak direct Offer visual reference.**

That distinction is important enough to lock before continuing the lab.
