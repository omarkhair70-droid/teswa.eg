# Teswa Phase 00 — Master Operating System

**Date:** 2026-09-17  
**Branch:** `audit/native-product-reality-20260917`  
**Tracking issue:** #524 — TESWA PHASE 00 — Legacy Erasure + Product Reality Excavation

## READ THIS FIRST

Teswa is **not** entering a cosmetic redesign.

The Play-tested Native v26 build proved that the new technical foundation can exist as a real update to the existing `com.teswa.mobile` app. That build is a technical/product-behavior checkpoint, not the visual design target.

From this point forward:

> **The old Expo product is evidence, not authority.**  
> **The current Native UI is a working instrument, not authority.**  
> **Oracle contracts and real product behavior are authority for runtime/business truth.**  
> **The new authored product system must be derived from Teswa itself before external UI references are allowed to shape it.**

---

# 1. Why the process changed

Earlier Teswa work often moved too quickly from “feature/product idea” to screens and implementation. That made it possible for inherited layouts, common marketplace patterns and old visual decisions to survive without re-earning their place.

The stronger workflow developed later across HILTECH, portfolio work and especially Fokhara changes the order.

## HILTECH lesson

Reality, brief, research, references, thesis, architecture, visual grammar, production and browser closure are separate gates.

A screenshot is not a brief.

A functioning implementation is not visual closure.

## Portfolio lesson

References must be decomposed:
- what transfers
- what does not
- why

Static composition must earn itself before motion decorates it.

## Fokhara lesson

The most important layer:

> Study the thing before studying websites about the thing.

Fokhara researched product/material/culture/science first, extracted meaning, translated meaning into digital behavior, wrote an authored thesis, and **only then** opened award/reference sites.

Teswa now adopts that maturity.

# 5. Phase 00 rules

## Rule A — No blind deletion

The cleanup starts with ownership/classification, not `rm -rf`.

A legacy file may still contain:
- migration truth
- rollback capability
- user-facing copy
- state edge cases
- real assets
- legal/store material
- operational scripts

Delete only after extracting what remains valuable.

## Rule B — No visual redesign yet

Do not spend Phase 00 changing:
- colors
- fonts
- card radii
- Home hero
- bottom navigation styling
- motion polish
- icon style

The current Compose UI is allowed to look provisional.

## Rule C — No marketplace references as identity source

Do not start by copying/decomposing Facebook Marketplace, Dubizzle, Vinted, Depop, OLX or design-gallery marketplace shots.

Later they can answer targeted questions such as:
- how a particular trust state is communicated
- how dense inventory is scanned
- how offer state is clarified
- how a known platform handles a specific edge case

They may challenge or benchmark Teswa's authored system. They may not generate the system.

## Rule D — Separate fact, evidence, hypothesis and thesis

Use explicit labels:
- OBSERVED
- SOURCE EVIDENCE
- HYPOTHESIS
- LOCKED PRINCIPLE

Do not let a promising phrase become product truth because it sounds good.

## Rule E — Product clarity beats concept performance

If the future authored system makes it harder to:
- understand an item
- know who owns it
- know what is being offered
- know conversation context
- know deal state
- assess trust
- take the next action

then the concept is wrong or over-applied.

# 8. Meaning Extraction gate — NOT OPEN YET

Do not yet lock concepts such as:
- “dormant value”
- “objects change hands”
- “truth accumulates”
- “mine ↔ yours”
- “proposal is the atomic unit”

They are candidates.

Meaning Extraction must reduce the source field aggressively.

A principle survives only if it passes:

1. **Product relevance** — true to real Teswa behavior.
2. **Source depth** — supported by more than a clever phrase.
3. **Generative power** — can influence multiple product surfaces coherently.
4. **Anti-cliché strength** — does not collapse into generic marketplace styling.
5. **Usability compatibility** — can coexist with exact transactional state.
6. **Native/device opportunity** — where appropriate, can benefit from Android interaction rather than merely web-like composition.

Expect to kill most source ideas.

# 11. Architecture before screens

After the thesis exists, define journeys and states before polishing individual routes.

Potential journey families to test:

### RELEASE
`I have something → make it available → receive interest → decide`

### SEEK
`I want / discover something → understand it → trust enough → propose`

### NEGOTIATE
`proposal → context → response → revised understanding → agreement/no agreement`

### COMPLETE
`agreement → practical handoff → outcome → reputation`

### PERSONAL WORLD
`identity → Dolab/inventory → history → relationships → active offers/deals`

These names are placeholders, not IA labels.

---

# 12. Design-system rule

Do not begin a “design system” by picking:
- 8px spacing
- radius scale
- surface colors
- button variants

First define the product grammar:

- what is stable?
- what changes state?
- what must carry context?
- what needs evidence?
- what marks commitment?
- what is exploratory vs transactional?
- what information gets denser as consequence rises?
- how does Arabic/RTL affect composition rather than only direction?

Tokens come after grammar.

# 13. Real-device closure rule

For every future major lane:

```text
reality recheck
→ targeted source/reference recheck
→ lane thesis
→ static/state prototype
→ implementation
→ physical Android review
→ capture
→ compare
→ correction
→ closure
```

A lane is not closed because:
- Kotlin compiles
- tests pass
- screenshot looks fine at one size
- AI says it is polished

Closure requires evidence on the actual product surface.

---

# 14. Authored Experiment Loop — later

Once the structural product system is stable, switch from construction to authorship:

```text
look
→ feel what is missing
→ targeted research
→ build one specific experiment
→ render on device
→ compare
→ KEEP / REWRITE / DELETE
→ integrate only what earns its place
→ recapture
→ subtract
→ repeat
```

Experiments are disposable by default.

Do not merge a lab simply because it contains many interesting ideas.

# Phase 00 success condition

Phase 00 is complete when:

1. legacy code can be deleted intentionally rather than emotionally;
2. every major current feature has a product-role verdict supported by evidence;
3. Teswa has a rich source world independent of competitor UI;
4. that source world has been reduced into a small locked Meaning System;
5. one authored product thesis exists;
6. the team can begin architecture/design without old Teswa or another marketplace silently deciding the answer.

Until then, the correct activity is **excavation, reduction and authorship — not decoration.**
